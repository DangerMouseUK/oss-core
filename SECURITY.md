# Security policy

`oss-core` is the shared half of Open SubSpace: the packet codecs, the transport
state machine, the file format parsers and the physics simulation. Almost
everything in it exists to turn bytes that arrived from somebody else into typed
values. That makes it the repository where a parsing bug matters most, and the
one most worth looking at.

## Reporting a vulnerability

**Use GitHub's private reporting, not a public issue.**

> **Security → Report a vulnerability**, or go straight to
> <https://github.com/DangerMouseUK/oss-core/security/advisories/new>

That opens a private thread with the maintainer. Nothing in it is visible to
anyone else unless and until an advisory is published.

**If you are not sure whether what you found is a security problem, report it
privately anyway.** Deciding that is our job, not yours, and a private report
that turns out to be an ordinary bug costs nothing. A public issue that turns
out to be a real vulnerability cannot be taken back.

## Which version

There are no releases and no tags yet, so there is no version table here and it
would be dishonest to invent one. **`main` is the only version there is.**

When you report something, say which commit you were on:

```sh
git rev-parse HEAD
```

## In scope

Anything reachable from bytes this crate set did not produce itself:

- **`oss-proto`** — packet decoding. Every packet type arrives from a peer.
- **`oss-net`** — the transport state machine: the reliable layer, clustering,
  file transfer, and the cipher implementations.
- **`oss-formats`** — `.lvl` maps, eLVL chunks, `.lvz` archives and `.ossr`
  replays, all of which are routinely downloaded from a server a user has only
  chosen to trust a little.
- **`oss-sim`** — the `validate` plausibility API in particular, because
  `oss-server`'s anti-cheat depends on it giving the right answer.

Specifically **in scope, and worth reporting even though it sounds minor**:

- **A panic on malformed input.** This crate set's rule is that decoders never
  panic and return `Result`. A panic is therefore a broken invariant that a
  caller cannot defend against, not a cosmetic fault — in a server it is a
  remote crash. Please send it.
- **Unbounded allocation or unbounded work** driven by attacker-controlled
  length or count fields.
- **Any `unsafe` that can be made to misbehave.**

If you want somewhere to start, [`fuzz/`](fuzz/) already has targets wired up
for several of these.

## Out of scope

- **A panic caused by the calling program misusing the API** in a way the
  documentation says not to. That is a bug — please file it as an ordinary
  issue — but it is not this policy's business.
- **Zones and servers other people run.** This project publishes software; it
  does not operate anybody's zone. If something is wrong with a zone you
  connected to, that belongs to whoever runs it.
- **Reports generated by a scanner with no analysis attached.** If a tool says
  there is a problem, tell us what an attacker would actually be able to do.

## What to expect

This is a volunteer project with one maintainer, and the honest answer is that
replies will not be instant.

- **Acknowledgement within seven days.** If you have heard nothing after that,
  the message went astray rather than being ignored — please ping the thread.
- We will tell you whether we think it is a real vulnerability, and why.
- If it is, we will fix it on `main` and publish an advisory. **You will be
  credited by whatever name you ask for, or not at all if you prefer.**
- We will not ask you to sit on something indefinitely. If we go quiet or cannot
  fix it, publishing is your call.

**There is no bug bounty**, and there is no funding to start one. This is
volunteer work on a twenty-eight-year-old game.

## One thing this policy is not for

This file is about **vulnerabilities in this code**. It is not a channel for
questions about what the project does or does not implement, or why. Those
belong in an ordinary issue.
