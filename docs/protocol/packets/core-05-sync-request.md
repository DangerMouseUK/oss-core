## Layout

| Offset | Size | Type | Field | Meaning |
|---|---|---|---|---|
| 0 | 1 | u8 | core | `0x00` |
| 1 | 1 | u8 | subtype | `0x05` |
| 2 | 4 | u32 | time | Sender's clock (ticks); before `00 02`, an id to echo back |
| 6 | 4 | u32 | sent | 14-byte form: datagrams sent |
| 10 | 4 | u32 | received | 14-byte form: datagrams received |

Integers are little-endian. `n` is a variable length; `i` counts repeated entries from 0.

## Notes

The 6-byte form has two roles. In an established session it is an ordinary sync, answered with `00 06` carrying the echoed value and the responder's own clock; clients send the 14-byte form and servers use the counts for loss statistics.

Before the connection is established it can also be a challenge that gates the connect response: subgame 1.34.14 answers `00 01` with a 6-byte `00 05` and sends nothing further until the client replies `00 06` with that `u32` echoed back, after which `00 02` arrives. Measured against that server: only the first `u32` of the reply is read, so the trailing clock is optional in this role. Why it requires the exchange is not known, and ASSS does not. See [encryption.md](../encryption.md).
